# Phase 1 Bybit Historical L2 Validation v4

## Purpose

Bybit’s official daily OrderBook archives are partitioned by UTC calendar date, while each record contains two exchange timestamps: `ts`, generated by the system, and `cts`, generated by the matching engine. Bybit also documents that a fresh snapshot can be resent after a service problem and that `u=1` can identify a service restart. The validator must preserve these source semantics without accepting arbitrary cross-day contamination. [1]

## Permanent boundary solution

The v4 rule is a **separately versioned, narrow first-record partition rule**. It does not widen the date window generally, discard the first record, or infer missing data.

A pre-start timestamp is accepted only when all of the following are true:

1. The record is the first non-empty record in the archive.
2. The record is a `snapshot`.
3. Both `ts` and `cts` are no earlier than `target_day_start_ms - 2,000`.
4. At least one of `ts` or `cts` is before `target_day_start_ms`, so the exception is recorded only when needed.
5. Every later record has both `ts >= target_day_start_ms` and `cts >= target_day_start_ms`.
6. `ts` and `cts` are non-decreasing over the complete archive.
7. The archive has no other validation failure.

The 2,000 ms bound is deterministic and inherited from the existing Phase 1 end-boundary grace. It is not selected using forward returns, event outcomes, signal performance, or any Phase 2–4 statistic.

This rule covers both observed official-source patterns: a first snapshot with `ts` in-window and `cts` slightly pre-start, and a first snapshot with both `ts` and `cts` slightly pre-start. It does not permit a pre-start timestamp on any later record.

## Snapshot-reset rule

The approved v2 rule remains included without modification. Exactly one mid-stream `snapshot` with `u=1` may occur only when its `seq` is strictly greater than the immediately previous `seq` and the next record has `u=2`. All other `u` and `seq` ordering, duplicate, level-shape, topic, symbol, ZIP, and end-boundary failures remain fatal except the pre-existing terminal snapshot duplicate convention. [1]

## Required validation and storage sequence

The worker must download only from the official Bybit URL, verify ZIP CRC/inflate integrity, require exactly one JSONL member, parse every non-empty record, verify topic and symbol, require integer timestamps and sequence fields, validate bid/ask level pairs, apply v4, compute the source SHA-256, upload to the symbol-specific Google Drive raw folder, restore by immutable Drive file ID, and require exact byte-count and SHA-256 equality. The manifest must record the rule version, source URL, source hash, Drive file ID, restored hash, validation report, and any boundary or snapshot-reset event.

Previously accepted archives are immutable checkpoint entries and must be skipped. They must not be reprocessed, overwritten, or rehashed merely because v4 is adopted.

## Fail-closed requirements

The original validator, v2 validator, and v3 validator must not be modified in place. No wider grace may be invented after a future failure. A file with a later pre-start timestamp, a first record outside the 2,000 ms grace, a non-snapshot first record, non-monotonic timestamps, unexplained sequence anomalies, corrupt ZIP data, topic/symbol mismatch, or Drive round-trip hash mismatch remains `VALIDATION_FAILED` and stops the sequential worker. Any future exception requires a new versioned rule, evidence, review, and explicit adoption.
